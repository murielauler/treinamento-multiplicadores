Fatia funcional

A1 · Escolher a fatia só proposta

Cole junto com a pasta/ZIP do projeto de ontem. Nada é implementado aqui.

Você está trabalhando em um projeto criado ontem por alunos durante uma aula.
Ele tem um front ou mock e pode ter uma proposta de banco, mas ainda não é uma
aplicação completa.

Tudo será feito com dados sintéticos, em sandbox descartável, para aprender
como front, backend e banco se comunicam. Não é um sistema de produção.
Prefira sempre o desenho pequeno, explícito e fácil de explicar.

SUA TAREFA AGORA
Apenas ESCOLHER a menor fatia vertical que demonstre:

formulário simples → POST /api/... → Supabase → GET /api/... → uma lista,
tabela ou card já existente no front.

A fatia deve representar o primeiro passo do processo desenhado no projeto.
Limites da escolha:
- UMA entidade principal, com 3 a 5 campos — entre eles pelo menos um número,
  uma data e uma escolha fechada (select);
- UMA tabela de negócio;
- opcionalmente UMA tabela de referência somente-leitura (ex.: obras,
  categorias), com 3 a 5 linhas de seed, ligada por FK e exibida como select
  no formulário;
- UMA rota POST e UMA rota GET (o GET pode ter no máximo um filtro);
- UMA tela ou componente que já existe no front.

Se o primeiro passo real for complexo — arquivo, OCR, IA, integração externa
ou muitas regras — represente-o por um formulário simples. Não desenhe a
complexidade futura.

MODO DE TRABALHO — REGRA ABSOLUTA
Você está em MODO PROPOSTA. Enquanto a mensagem do aluno não for exatamente
APROVAR:
- não crie, altere ou exclua nenhum arquivo;
- não instale nada, não configure nada, não escreva em banco nenhum;
- responda ao feedback ajustando a proposta;
- termine cada resposta com: “Aguardando APROVAR. Não fiz alterações.”

PRIMEIRA RESPOSTA — O QUADRO DA FATIA
Inspecione o projeto e responda somente com este quadro preenchido:

═══════════════ FATIA ESCOLHIDA ═══════════════
1. NOME DA FATIA: (uma frase: o que ela demonstra)
2. PASSO DO PROCESSO: qual primeiro passo real ela representa
3. TABELAS:
   - negócio: nome + campos com tipos
   - referência (se houver): nome + linhas do seed
4. AÇÕES DO USUÁRIO: o que dá para FAZER na tela
   (ex.: cadastrar X, ver a lista de X filtrada por Y)
5. TELA: qual componente existente vai mostrar os dados
6. ROTAS: POST /api/... (o que grava) · GET /api/... (o que devolve e filtro)
7. FORA DESTA FATIA: lista explícita do que NÃO entra
8. CRITÉRIOS DE ACEITE: três, verificáveis
═══════════════════════════════════════════════

Depois pare e aguarde. O aluno pode criticar e pedir mudanças em linguagem
natural quantas vezes quiser.

QUANDO RECEBER APROVAR
Crie somente UM arquivo: docs/fatia-aprovada.md, com o quadro final aprovado.
Nada além disso — banco é o próximo prompt. Confirme com:
“Fatia registrada em docs/fatia-aprovada.md. Próximo passo: banco de dados.”

A2 · Banco no Supabase docs/fatia-aprovada.md

Use depois do A1 aprovado. O Claude para e espera CREDENCIAL CONFIGURADA.

Leia docs/fatia-aprovada.md. Sua tarefa agora é implementar SOMENTE o banco
de dados dessa fatia no Supabase. Nada de backend, front ou deploy.

PASSO 1 — CREDENCIAL (antes de qualquer coisa)
1. Crie ou atualize .env.example com os nomes SUPABASE_URL e
   SUPABASE_SERVICE_ROLE_KEY, sem valores.
2. Confirme que .env.local está no .gitignore (se o projeto ignora .env*,
   mantenha a exceção !.env.example).
3. PARE e instrua o aluno a:
   - abrir o painel do Supabase → Settings → API;
   - copiar a Project URL e a service_role key;
   - colar as duas em .env.local, manualmente, no editor;
   - responder no chat somente CREDENCIAL CONFIGURADA.
4. Nunca peça a credencial no chat. Não abra, imprima ou repita o valor
   de .env.local.

PASSO 2 — DEPOIS DE CREDENCIAL CONFIGURADA
1. Escreva o SQL mínimo da fatia aprovada:
   - a tabela de negócio, com os tipos do quadro;
   - a tabela de referência com o seed, se o quadro tiver;
   - FK entre elas, se o quadro tiver;
   - RLS HABILITADO nas tabelas (o acesso será só pelo backend com a
     service role — não crie policies de acesso público).
2. Aplique o SQL usando a conexão configurada. Se não for possível aplicar
   direto, entregue o SQL num bloco único e guie o aluno a colar no
   SQL Editor do Supabase — depois verifique.
3. PROVE que funcionou: rode um select nas tabelas e mostre o resultado
   (o seed da referência deve aparecer).

NÃO FAÇA
- tabelas além das do quadro aprovado;
- colunas “para o futuro”;
- desligar RLS ou criar policy pública;
- backend, front, IA ou deploy.

Ao terminar, entregue: o SQL aplicado, a prova do select e a frase
“Banco pronto. Próximo passo: backend e tela.”

A3 · Backend e tela POST + GET + front

Use depois do A2. Fecha a fatia: dado atravessando do formulário à tela.

Leia docs/fatia-aprovada.md. O banco já existe no Supabase (prompt anterior).
Sua tarefa agora é implementar o backend e ligar a tela — exatamente o que o
quadro aprovado descreve, nada além.

ARQUITETURA OBRIGATÓRIA
- preserve o front e a stack existentes;
- se for Next.js, use Route Handlers em /api;
- o front chama apenas /api/... e NUNCA acessa o Supabase diretamente;
- o backend usa as variáveis de .env.local (server-side);
- secret/service key nunca aparece no front nem em NEXT_PUBLIC_;
- somente as rotas do quadro: um POST e um GET (com o filtro aprovado,
  se houver).

ORDEM
1. Mostre o plano de arquivos (criados e alterados) antes de começar.
2. Implemente e teste o POST — valide os tipos; input inválido recebe
   erro legível.
3. Implemente e teste o GET (com o filtro, se aprovado).
4. Ligue SOMENTE a tela do quadro, preservando o visual do mock. Se houver
   tabela de referência, o select do formulário vem do banco.
5. Implemente loading, erro e atualização após envio apenas nessa fatia.
6. Rode os três critérios de aceite do quadro.
7. Prove que o refresh preserva o registro.

NÃO FAÇA
- completar outras telas ou botões;
- autenticação, papéis ou permissões;
- IA, OCR, upload, storage ou integração externa;
- editar, excluir, aprovar ou notificar;
- refatorar o front ou criar arquitetura para o produto inteiro;
- adicionar algo “útil” que não está no quadro.

Se precisar sair do escopo do quadro, PARE e explique. Não amplie por conta
própria.

DEFINIÇÃO DE PRONTO
- um input válido aparece no Supabase;
- a tela mostra o registro por meio do GET;
- após refresh, o registro continua aparecendo;
- input inválido recebe erro legível;
- nenhuma chave secreta está no cliente.

Ao terminar, entregue: arquivos alterados, como rodar, evidências dos três
critérios de aceite e o que ficou fora do escopo. Não publique — o deploy é
outro prompt.

Decisão com IA

B1 · Escolher a decisão só proposta

Use com a fatia A funcionando. Nada é implementado aqui.

O projeto já tem uma fatia funcional: um input é gravado no Supabase e uma
tela lê os dados pelo backend (veja docs/fatia-aprovada.md).

Tudo continua sintético e em sandbox. O fluxo que vamos aprender:
banco → backend → LLM → decisão registrada → revisão humana. A LLM apenas
SUGERE: ela não altera o registro original nem executa ações externas.

SUA TAREFA AGORA
Apenas ESCOLHER uma decisão pequena em que uma LLM possa ajudar a partir de
UM registro já salvo no banco.

UMA BOA DECISÃO PARA A AULA
- usa um único registro existente;
- devolve categoria, prioridade, status sugerido ou próximo passo curto;
- possui de 2 a 5 respostas permitidas;
- pode ser conferida por uma pessoa em menos de 30 segundos;
- o erro é reversível e fica restrito à tabela decisoes_ia;
- permite criar 3 exemplos sintéticos com resposta esperada;
- depende de interpretação de texto; se if/else resolver, não force LLM.

NÃO ESCOLHA
- aprovar pagamento, contrato, pessoa ou lançamento;
- decisão jurídica, médica, financeira, trabalhista ou de segurança;
- calcular totais, impostos ou reconciliações;
- gerar texto livre longo;
- alterar o registro original ou disparar ações;
- dados pessoais, confidenciais ou reais;
- agente, RAG, vetor ou multiagente;
- tarefa sem resposta verificável.

MODO DE TRABALHO — REGRA ABSOLUTA
Você está em MODO PROPOSTA. Enquanto a mensagem do aluno não for exatamente
APROVAR:
- não crie ou altere arquivos, banco ou dependências;
- não chame nenhuma LLM;
- ajuste a proposta conforme o feedback;
- termine cada resposta com: “Aguardando APROVAR. Não fiz alterações.”

PRIMEIRA RESPOSTA — O QUADRO DA DECISÃO
Avalie até 3 decisões candidatas numa tabela curta (nome · registro de
origem · campos usados · saídas permitidas · como o humano verifica · risco
se errar · por que LLM e não regra · nota 1-5 de adequação à aula).

Recomende UMA. Se regra determinística for melhor, diga isso.

Para a recomendada, preencha:

═══════════════ DECISÃO ESCOLHIDA ═══════════════
1. PERGUNTA EXATA que a IA responde
2. tipo_decisao (identificador curto)
3. CAMPOS enviados à LLM (somente os necessários)
4. JSON EXATO de resposta (com as opções permitidas)
5. 3 EXEMPLOS sintéticos e a saída esperada de cada um
6. TELA única onde a sugestão vai aparecer
7. NÃO SERÁ IMPLEMENTADO: lista explícita
═════════════════════════════════════════════════

Depois pare e aguarde APROVAR.

QUANDO RECEBER APROVAR
Crie somente UM arquivo: docs/decisao-aprovada.md, com o quadro final.
Nada além disso. Confirme com:
“Decisão registrada em docs/decisao-aprovada.md. Próximo passo: a tabela.”

Leia docs/decisao-aprovada.md. Sua tarefa agora é criar SOMENTE a tabela

A TABELA
Crie decisoes_ia no Supabase (conexão já configurada em .env.local):

RLS habilitado, sem policy pública — o acesso é só pelo backend.

Aplique o SQL pela conexão; se não for possível, entregue o bloco único e
guie o aluno no SQL Editor. Depois PROVE com um select que a tabela existe
e que a FK aponta para a tabela certa.

NÃO FAÇA
- outras tabelas ou colunas além destas;
- backend, chamada de LLM, tela ou deploy;
- alterar as tabelas da fatia A.

Ao terminar: SQL aplicado, prova do select e a frase
“Tabela pronta. Próximo passo: backend e LLM.”

B3 · Backend e LLM simulação → chave → real

Use depois do B2. O Claude para e espera CHAVE CONFIGURADA antes da OpenAI real.

Leia docs/decisao-aprovada.md. O banco já tem a tabela decisoes_ia. Sua
tarefa agora é implementar a rota, a chamada à LLM e a exibição na tela.

PROVEDOR DA AULA
Use exclusivamente um modelo GPT pela OpenAI API, com o SDK oficial
JavaScript `openai` e a Responses API. Não automatize a interface do ChatGPT
e não use outro provedor. Modelo em OPENAI_MODEL, chave em OPENAI_API_KEY —
sempre server-side.

A ROTA
Crie somente POST /api/decisoes, que:
- recebe apenas o ID do registro de origem;
- busca o registro no Supabase, no backend;
- seleciona apenas os campos do quadro aprovado;
- chama a LLM no backend, exigindo saída estruturada no JSON aprovado;
- rejeita saída fora das opções permitidas;
- grava entrada, resultado e metadados em decisoes_ia;
- devolve a decisão criada ou erro legível.

O registro original NUNCA é alterado. A sugestão aparece somente na tela do
quadro aprovado, com a justificativa.

ORDEM DE IMPLEMENTAÇÃO
1. Mostre o plano de arquivos.
2. Implemente o POST com resposta SIMULADA fixa e prove a gravação em
   decisoes_ia.
3. PAUSA DA CHAVE — antes da primeira chamada real:
   - adicione OPENAI_API_KEY e OPENAI_MODEL ao .env.example, sem valores;
   - PARE e instrua o aluno a criar a key no painel da OpenAI, colar em
     .env.local no editor, preencher OPENAI_MODEL, salvar e responder no
     chat somente CHAVE CONFIGURADA;
   - nunca peça a chave no chat; não leia nem repita o valor de .env.local.
4. Depois de CHAVE CONFIGURADA, troque a simulação pela Responses API.
5. Valide o JSON antes de gravar.
6. Mostre a sugestão na tela aprovada.
7. Rode os 3 exemplos do quadro e compare esperado vs. obtido, numa tabela.

NÃO IMPLEMENTE
- mudança automática no registro original;
- aceitar/rejeitar, salvo se a facilitadora pedir depois;
- lote, fila, cron, webhook ou integração;
- texto fora do JSON aprovado;
- “confiança” inventada pela LLM como probabilidade calibrada;
- uma segunda decisão.

Se precisar de outra tabela, outra rota ou uma ação real, PARE e explique.

DEFINIÇÃO DE PRONTO
- backend recebe apenas um ID;
- só os campos aprovados chegam à LLM;
- saída é JSON válido dentro da taxonomia;
- sugestão registrada em decisoes_ia; original intacto;
- tela mostra sugestão e justificativa;
- os 3 testes documentados (esperado vs. obtido);
- nenhuma chave no cliente ou no repositório.

Ao terminar: arquivos alterados, resultado dos 3 testes, limites conhecidos
e o que ficou fora do escopo.

Publicar na Vercel

C · Deploy preview deployment

Use com tudo funcionando localmente. O Claude para e espera VARIAVEIS CONFIGURADAS.

Você está trabalhando em um protótipo funcional criado por alunos durante uma
aula. O fluxo já funciona localmente e agora queremos publicá-lo na Vercel para
enxergar como front e backend passam a responder por uma URL na internet.

Este é um sandbox temporário com dados sintéticos. A publicação serve para
aprendizado e demonstração; não é produção e não autoriza uso com dados reais.

OBJETIVO
Publicar exatamente o projeto atual como uma Preview Deployment da Vercel,
preservando o front, as rotas de backend e o schema existentes.

MODO DE TRABALHO — REGRA ABSOLUTA
Você começa em MODO PROPOSTA.

Enquanto a mensagem do aluno não for exatamente APROVAR:
- não faça deploy;
- não crie projeto na Vercel;
- não altere arquivos ou configurações remotas;
- não instale dependências;
- inspecione e explique o plano;
- ajuste o plano conforme o feedback do aluno;
- termine cada resposta com:
  “Aguardando APROVAR. Não fiz deploy nem alterações.”

Somente quando o aluno responder exatamente APROVAR, execute a versão mais
recente do plano.

PRIMEIRA RESPOSTA — SEM ALTERAR OU PUBLICAR
Inspecione o projeto e responda somente com:

A. framework e comando de build encontrados;
B. rotas de backend que serão publicadas;
C. nomes das variáveis de ambiente necessárias, sem valores;
D. confirmação de que secrets não estão no código, Git ou variáveis públicas;
E. arquivos mínimos que precisam ser ajustados, se houver;
F. comando ou fluxo de deploy que pretende usar;
G. cinco testes que fará na URL;
H. lista do que não será alterado.

Prefira o fluxo mais simples para a máquina atual:
- usar a Vercel CLI pelo projeto, por exemplo `npx vercel`, sem exigir
  instalação global;
- criar uma Preview Deployment, não usar `--prod`;
- se o repositório já estiver conectado à Vercel, reutilizar a configuração;
- usar o diretório correto do app, sem publicar o ZIP inteiro por engano.

Depois pare e aguarde APROVAR.

DEPOIS DE APROVAR
1. Confirme que `.env*` e arquivos de credencial estão no `.gitignore`.
2. Rode o build de produção local. Se falhar, corrija somente o necessário para
   o build/deploy, sem mudar funcionalidade, schema ou visual.
3. Faça login na Vercel somente pelo fluxo oficial. Se for necessária uma ação
   humana no navegador ou terminal, PARE, dê uma instrução por vez e aguarde.
4. Crie ou conecte o projeto da Vercel.
5. Se o app exigir secrets do Supabase ou da OpenAI, PARE antes do deploy e
   instrua o aluno a abrir Vercel → Project → Settings → Environment Variables,
   criar as variáveis necessárias e colar os valores diretamente no painel.
   Para OpenAI, os nomes são `OPENAI_API_KEY` e `OPENAI_MODEL`.
6. Peça que o aluno responda no chat somente `VARIAVEIS CONFIGURADAS`.
7. Nunca peça que o aluno cole secrets no chat, nunca mostre seus valores e
   nunca coloque secrets no código ou em variáveis `NEXT_PUBLIC_`.
8. Depois de `VARIAVEIS CONFIGURADAS`, faça uma Preview Deployment. Não use
   domínio customizado e não promova para Production.
9. Confirme que o front usa caminhos relativos como `/api/...`, sem URL de
   localhost hard-coded.
10. Teste a URL publicada.

TESTES OBRIGATÓRIOS NA URL
- página principal abre;
- GET da fatia retorna dados do Supabase;
- POST válido grava um novo registro;
- refresh mostra o registro persistido;
- POST inválido devolve erro legível;
- se a fatia com LLM tiver sido implementada, uma sugestão é gravada em
  `decisoes_ia` sem alterar o registro original.

SEGURANÇA MÍNIMA DO SANDBOX
- somente dados sintéticos;
- limite pequeno de tamanho/quantidade no input;
- nenhum secret no navegador, resposta HTTP ou log entregue ao aluno;
- recomendar remover a Preview e o projeto de banco ao fim da atividade;
- se houver Deployment Protection disponível e já configurada, manter ativa;
  não comprar plano ou add-on para esta aula.

NÃO FAZER
- não redesenhar o app;
- não trocar framework;
- não criar CI/CD, domínio, analytics ou observabilidade;
- não adicionar autenticação ou requisitos de produção;
- não refatorar código que já funciona;
- não alterar tabelas para “melhorar” a arquitetura;
- não declarar que o sistema está em produção.

Se o deploy exigir credencial, autorização ou escolha que só o aluno pode
fazer, PARE e peça apenas essa ação. Não contorne permissões.

Ao terminar, entregue somente:
1. URL da Preview;
2. URL/caminhos das rotas testadas, sem secrets;
3. resultado dos testes;
4. variáveis configuradas, apenas os nomes;
5. qualquer limite conhecido;
6. como remover o deploy depois da aula.
