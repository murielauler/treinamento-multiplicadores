Dia 2

Três prompts, com aprovação humana

Um prompt por aprendizado:

A · Fatia funcional — input → backend → Supabase → front
B · Decisão com IA — banco → backend → LLM → decisoes_ia → front
C · Deploy — projeto local → build → Vercel → URL de Preview

As duas fases de cada prompt

  1. Antes de APROVAR: o Claude só inspeciona e propõe. Você conversa normalmente, critica e pede mudanças. Nenhum código pode ser alterado.
  2. Depois de APROVAR: o Claude implementa exatamente a última proposta.

Você não precisa preencher contrato nem colar um segundo prompt. Se não gostar da proposta, responda como gente:

Está grande demais. Use só quatro campos e mostre na tabela que já existe.

Quando estiver satisfeito, responda somente:

APROVAR

Contexto da aula

Tudo é feito com dados sintéticos, em sandbox descartável, para aprender como as camadas se comunicam. Não é um sistema autorizado para uso real e não deve ser descrito como “produção”. A entrega máxima é um protótipo didático funcional publicado.
Prompt A

Input, Supabase e front

Cole este prompt junto com a pasta/ZIP do projeto que vocês fizeram ontem.

O prompt fatia vertical

Você está trabalhando em um projeto criado ontem por alunos durante uma aula.
Ele tem um front ou mock e pode ter uma proposta de banco, mas ainda não é uma
aplicação completa.

CONTEXTO DIDÁTICO
Tudo será feito com dados sintéticos, em sandbox descartável. O objetivo é
aprender como front, backend e banco se comunicam — não construir ou autorizar
um sistema de produção. Prefira código pequeno, explícito e fácil de explicar.

OBJETIVO
Implementar a menor fatia vertical possível que demonstre:

formulário simples → POST /api/... → Supabase → GET /api/... → uma lista,
tabela ou card já existente no front.

A fatia deve representar o primeiro passo do processo desenhado no projeto.
Escolha somente:
- UMA entidade principal;
- 3 a 5 campos;
- UMA tabela de negócio;
- UMA rota POST;
- UMA rota GET;
- UMA tela ou componente já existente.

Se o primeiro passo real for complexo — arquivo, OCR, IA, integração externa
ou muitas regras — represente-o nesta aula por um formulário de 3 a 5 campos.
Não implemente a complexidade futura.

MODO DE TRABALHO — REGRA ABSOLUTA
Você começa em MODO PROPOSTA.

Enquanto a mensagem do aluno não for exatamente APROVAR:
- não crie, altere ou exclua arquivos;
- não escreva no banco;
- não instale dependências;
- não configure ou publique serviços;
- responda ao feedback ajustando a proposta;
- termine cada resposta com:
  “Aguardando APROVAR. Não fiz alterações.”

Somente quando o aluno responder exatamente APROVAR, implemente a versão mais
recente da proposta. APROVAR não autoriza ampliar o escopo.

NÃO FAZ PARTE
- completar outras telas ou botões;
- autenticação, papéis ou permissões;
- IA, OCR, agentes ou classificação automática;
- upload ou storage de arquivos;
- integrações externas;
- editar, excluir, aprovar ou notificar;
- refatorar ou redesenhar todo o front;
- criar arquitetura para o produto inteiro;
- adicionar algo “útil” que não foi pedido.

ARQUITETURA OBRIGATÓRIA
- preserve o front e a stack existentes sempre que possível;
- se já for Next.js, use Route Handlers em /api;
- o front chama apenas /api/... e não acessa o Supabase diretamente;
- o backend usa variáveis server-side;
- secret/service key nunca aparece no front ou em NEXT_PUBLIC_;
- use no máximo uma tabela de negócio nova;
- crie no máximo um POST e um GET.

PRIMEIRA RESPOSTA — SEM IMPLEMENTAR
Inspecione o projeto e responda somente com:

A. primeiro passo do processo encontrado;
B. entidade escolhida e seus 3 a 5 campos;
C. tabela usada ou criada;
D. POST e o que grava;
E. GET e o que devolve;
F. única tela/componente conectado;
G. arquivos que seriam criados ou alterados;
H. três critérios de aceite;
I. lista “não será implementado”.

Depois pare e aguarde APROVAR.

DEPOIS DE APROVAR — IMPLEMENTAÇÃO
1. Verifique scripts e padrões já existentes.
2. Mostre o plano imediato de arquivos.
3. Crie ou ajuste apenas o SQL mínimo.
4. Implemente e teste o POST.
5. Implemente e teste o GET.
6. Ligue somente a tela aprovada, preservando o visual.
7. Implemente loading, erro e atualização após envio apenas nessa fatia.
8. Rode os três critérios de aceite.
9. Prove que o refresh preserva o registro.
10. Se precisar sair do escopo, PARE e explique. Não amplie por conta própria.

DEFINIÇÃO DE PRONTO
- um input válido aparece no Supabase;
- a tela mostra o registro por meio do GET;
- após refresh, o registro continua aparecendo;
- input inválido recebe erro legível;
- nenhuma chave secreta está no cliente;
- o resto do mock permanece fora do escopo.

Ao terminar, entregue:
1. arquivos alterados;
2. variáveis necessárias, sem valores;
3. como rodar;
4. evidências dos critérios de aceite;
5. o que permaneceu fora do escopo.

Não publique. O deploy será feito separadamente com o Prompt C.

O que você avalia antes de aprovar

Se não, peça mudanças com suas próprias palavras. Não há prompt de correção obrigatório.

Prompt B

Uma sugestão da LLM registrada no banco

Use somente depois que a primeira fatia estiver funcionando. Cole uma vez.

O prompt decisoes_ia

Você está trabalhando em um protótipo criado por alunos em uma aula. O projeto
já tem uma fatia funcional: um input é gravado no Supabase e uma tela lê os
dados por meio do backend.

CONTEXTO DIDÁTICO
Tudo será feito com dados sintéticos, em sandbox descartável. O objetivo é
aprender o fluxo banco → backend → LLM → decisão registrada → revisão humana.
Não estamos construindo ou autorizando um sistema de produção. A LLM apenas
sugere; ela não altera o registro original nem executa ações externas.

PROVEDOR DA AULA
Use exclusivamente um modelo GPT por meio da OpenAI API, com o SDK oficial
JavaScript `openai` e a Responses API. Não automatize a interface do ChatGPT e
não use outro provedor. O modelo deve vir da variável server-side
`OPENAI_MODEL`; a chave deve vir de `OPENAI_API_KEY`.

OBJETIVO
Encontrar e depois implementar UMA decisão pequena em que uma LLM possa ajudar
a partir de UM registro já salvo no banco.

Fluxo obrigatório:

registro existente → backend busca pelo ID → envia poucos campos à LLM
→ valida JSON → grava em decisoes_ia → mostra a sugestão no front

UMA BOA DECISÃO PARA A AULA
- usa um único registro existente;
- devolve categoria, prioridade, status sugerido ou próximo passo curto;
- possui de 2 a 5 respostas permitidas;
- pode ser conferida por uma pessoa em menos de 30 segundos;
- o erro é reversível e fica restrito a `decisoes_ia`;
- permite criar 3 exemplos sintéticos com resposta esperada;
- depende de interpretação de texto; se if/else resolver, não force LLM.

NÃO ESCOLHA
- aprovar pagamento, contrato, pessoa ou lançamento;
- decisão jurídica, médica, financeira, trabalhista ou de segurança;
- calcular totais, impostos ou reconciliações;
- gerar texto livre longo;
- alterar o registro original;
- enviar mensagens ou disparar ações;
- usar dados pessoais, confidenciais ou reais;
- criar agente, RAG, vetor ou multiagente;
- tarefa sem resposta verificável.

MODO DE TRABALHO — REGRA ABSOLUTA
Você começa em MODO PROPOSTA.

Enquanto a mensagem do aluno não for exatamente APROVAR:
- não crie ou altere arquivos, banco ou dependências;
- não chame uma LLM;
- apresente ou ajuste a proposta conforme o feedback do aluno;
- termine cada resposta com:
  “Aguardando APROVAR. Não fiz alterações.”

Somente quando o aluno responder exatamente APROVAR, implemente a versão mais
recente da proposta. APROVAR não autoriza ampliar o escopo.

PRIMEIRA RESPOSTA — SEM IMPLEMENTAR
Avalie até 3 decisões candidatas em uma tabela com:

1. nome da decisão;
2. tabela/registro de origem;
3. campos usados;
4. opções de saída permitidas;
5. como o humano verifica;
6. risco se errar;
7. por que LLM e não regra simples;
8. adequação à aula, de 1 a 5.

Recomende UMA candidata. Se regra determinística for melhor, diga isso.

Para a recomendada, mostre:
- pergunta exata respondida pela IA;
- `tipo_decisao`;
- campos enviados à LLM;
- JSON exato de resposta;
- 3 exemplos sintéticos e saída esperada;
- única tela onde a sugestão aparecerá;
- lista “não será implementado”.

Depois pare e aguarde APROVAR.

DEPOIS DE APROVAR — ESCOPO TÉCNICO
Crie somente uma tabela nova, `decisoes_ia`, com:
- id;
- registro_origem_id;
- tipo_decisao;
- entrada_snapshot em JSON;
- resultado em JSON;
- modelo;
- prompt_versao;
- status (`sugerida`, `aceita`, `rejeitada`), iniciando em `sugerida`;
- criado_em.

Crie somente uma rota nova, POST `/api/decisoes`, que:
- recebe apenas o ID do registro de origem;
- busca o registro no Supabase no backend;
- seleciona apenas os campos aprovados;
- chama a LLM no backend;
- exige o JSON aprovado;
- rejeita saída fora das opções permitidas;
- grava entrada, resultado e metadados em `decisoes_ia`;
- devolve a decisão criada ou erro legível.

Mostre a sugestão somente na tela aprovada. Mantenha chaves do Supabase e da
OpenAI apenas em variáveis server-side, nunca em NEXT_PUBLIC_. Use o SDK
oficial da OpenAI e a Responses API. Exija uma saída estruturada que corresponda
ao JSON aprovado antes de gravar.

PAUSA OBRIGATÓRIA PARA A CHAVE DA OPENAI
Depois que a resposta simulada estiver funcionando e antes da primeira chamada
real à OpenAI:

1. Crie ou atualize somente `.env.example`, contendo os nomes
   `OPENAI_API_KEY` e `OPENAI_MODEL`, sem valores reais.
2. Confirme que `.env.local` está no `.gitignore`. Se o projeto ignora
   `.env*`, mantenha a exceção `!.env.example`, pois esse arquivo contém apenas
   nomes e pode ser compartilhado.
3. PARE e instrua o aluno a:
   - criar uma API key diretamente no painel da OpenAI;
   - abrir ou criar `.env.local` manualmente no editor;
   - colar a chave diretamente nesse arquivo como `OPENAI_API_KEY=...`;
   - preencher `OPENAI_MODEL` com o modelo GPT disponível para a aula;
   - salvar o arquivo e reiniciar o servidor local, se necessário;
   - responder no chat somente `CHAVE CONFIGURADA`.
4. Nunca peça que o aluno cole a chave no chat. Não abra, leia, imprima,
   registre ou repita o valor de `.env.local`.
5. Só depois de receber `CHAVE CONFIGURADA`, faça a chamada real e os testes.

NÃO IMPLEMENTE
- mudança automática no registro original;
- aceitar/rejeitar, salvo se a facilitadora pedir depois;
- lote, fila, cron, webhook ou integração;
- texto fora do JSON aprovado;
- “confiança” inventada pela LLM como probabilidade calibrada;
- uma segunda decisão;
- requisitos de produção.

ORDEM DE IMPLEMENTAÇÃO
1. Mostre os arquivos que serão alterados.
2. Crie `decisoes_ia`.
3. Implemente o POST com resposta simulada fixa e prove a gravação.
4. Faça a pausa obrigatória de credencial descrita acima.
5. Após `CHAVE CONFIGURADA`, substitua a simulação pela OpenAI Responses API.
6. Valide o JSON antes de gravar.
7. Mostre a sugestão na tela aprovada.
8. Rode os 3 exemplos e compare esperado vs. obtido.

DEFINIÇÃO DE PRONTO
- backend recebe apenas um ID;
- registro é lido do banco no servidor;
- só os campos aprovados chegam à LLM;
- saída é JSON válido dentro da taxonomia;
- sugestão fica registrada em `decisoes_ia`;
- tela mostra sugestão e justificativa;
- registro original permanece inalterado;
- três testes estão documentados;
- nenhuma chave aparece no cliente ou repositório.

Se precisar de outra tabela, outra rota ou uma ação real, PARE e explique. Não
amplie por conta própria.

Ao terminar, entregue:
1. arquivos alterados;
2. SQL criado;
3. variáveis necessárias, sem valores;
4. resultado dos 3 testes;
5. limites conhecidos e itens fora do escopo.

O que você avalia antes de aprovar a decisão

  • Qual pergunta exata a IA responde?
  • Quais respostas são permitidas?
  • Por que if/else não basta?
  • Como uma pessoa verifica a sugestão?
  • O que acontece quando a IA erra?

Converse normalmente até ficar satisfeito e então escreva apenas APROVAR.

Prompt C

O prompt preview deployment

Você está trabalhando em um protótipo funcional criado por alunos durante uma
aula. O fluxo já funciona localmente e agora queremos publicá-lo na Vercel para
enxergar como front e backend passam a responder por uma URL na internet.

CONTEXTO DIDÁTICO
Este é um sandbox temporário com dados sintéticos. A publicação serve para
aprendizado e demonstração; não é produção e não autoriza uso com dados reais.

OBJETIVO
Publicar exatamente o projeto atual como uma Preview Deployment da Vercel,
preservando o front, as rotas de backend e o schema existentes.

MODO DE TRABALHO — REGRA ABSOLUTA
Você começa em MODO PROPOSTA.

Enquanto a mensagem do aluno não for exatamente APROVAR:
- não faça deploy;
- não crie projeto na Vercel;
- não altere arquivos ou configurações remotas;
- não instale dependências;
- inspecione e explique o plano;
- ajuste o plano conforme o feedback do aluno;
- termine cada resposta com:
  “Aguardando APROVAR. Não fiz deploy nem alterações.”

Somente quando o aluno responder exatamente APROVAR, execute a versão mais
recente do plano.

PRIMEIRA RESPOSTA — SEM ALTERAR OU PUBLICAR
Inspecione o projeto e responda somente com:

A. framework e comando de build encontrados;
B. rotas de backend que serão publicadas;
C. nomes das variáveis de ambiente necessárias, sem valores;
D. confirmação de que secrets não estão no código, Git ou variáveis públicas;
E. arquivos mínimos que precisam ser ajustados, se houver;
F. comando ou fluxo de deploy que pretende usar;
G. cinco testes que fará na URL;
H. lista do que não será alterado.

Prefira o fluxo mais simples para a máquina atual:
- usar a Vercel CLI pelo projeto, por exemplo `npx vercel`, sem exigir
  instalação global;
- criar uma Preview Deployment, não usar `--prod`;
- se o repositório já estiver conectado à Vercel, reutilizar a configuração;
- usar o diretório correto do app, sem publicar o ZIP inteiro por engano.

Depois pare e aguarde APROVAR.

DEPOIS DE APROVAR
1. Confirme que `.env*` e arquivos de credencial estão no `.gitignore`.
2. Rode o build de produção local. Se falhar, corrija somente o necessário para
   o build/deploy, sem mudar funcionalidade, schema ou visual.
3. Faça login na Vercel somente pelo fluxo oficial. Se for necessária uma ação
   humana no navegador ou terminal, PARE, dê uma instrução por vez e aguarde.
4. Crie ou conecte o projeto da Vercel.
5. Se o app exigir secrets do Supabase ou da OpenAI, PARE antes do deploy e
   instrua o aluno a abrir Vercel → Project → Settings → Environment Variables,
   criar as variáveis necessárias e colar os valores diretamente no painel.
   Para OpenAI, os nomes são `OPENAI_API_KEY` e `OPENAI_MODEL`.
6. Peça que o aluno responda no chat somente `VARIAVEIS CONFIGURADAS`.
7. Nunca peça que o aluno cole secrets no chat, nunca mostre seus valores e
   nunca coloque secrets no código ou em variáveis `NEXT_PUBLIC_`.
8. Depois de `VARIAVEIS CONFIGURADAS`, faça uma Preview Deployment. Não use
   domínio customizado e não promova para Production.
9. Confirme que o front usa caminhos relativos como `/api/...`, sem URL de
   localhost hard-coded.
10. Teste a URL publicada.

TESTES OBRIGATÓRIOS NA URL
- página principal abre;
- GET da fatia retorna dados do Supabase;
- POST válido grava um novo registro;
- refresh mostra o registro persistido;
- POST inválido devolve erro legível;
- se a fatia com LLM tiver sido implementada, uma sugestão é gravada em
  `decisoes_ia` sem alterar o registro original.

SEGURANÇA MÍNIMA DO SANDBOX
- somente dados sintéticos;
- limite pequeno de tamanho/quantidade no input;
- nenhum secret no navegador, resposta HTTP ou log entregue ao aluno;
- recomendar remover a Preview e o projeto de banco ao fim da atividade;
- se houver Deployment Protection disponível e já configurada, manter ativa;
  não comprar plano ou add-on para esta aula.

NÃO FAZER
- não redesenhar o app;
- não trocar framework;
- não criar CI/CD, domínio, analytics ou observabilidade;
- não adicionar autenticação ou requisitos de produção;
- não refatorar código que já funciona;
- não alterar tabelas para “melhorar” a arquitetura;
- não declarar que o sistema está em produção.

Se o deploy exigir credencial, autorização ou escolha que só o aluno pode
fazer, PARE e peça apenas essa ação. Não contorne permissões.

Ao terminar, entregue somente:
1. URL da Preview;
2. URL/caminhos das rotas testadas, sem secrets;
3. resultado dos testes;
4. variáveis configuradas, apenas os nomes;
5. qualquer limite conhecido;
6. como remover o deploy depois da aula.

Debrief

  • A LLM decidiu ou sugeriu?
  • Qual dado saiu do banco e chegou ao modelo?
  • Onde a resposta ficou registrada?
  • O que impede uma saída fora da taxonomia?
  • Em quais exemplos ela errou?
  • Ainda parece melhor que uma regra simples?

Para a facilitadora

Parar a dupla se o Claude
  • alterar código antes de APROVAR;
  • criar mais de uma tabela de negócio;
  • propor upload, IA ou auth “já que estamos aqui” na primeira fatia;
  • substituir todo o mock;
  • conectar o navegador diretamente com secret/service key;
  • implementar ação automática a partir da sugestão da LLM;
  • declarar sucesso sem mostrar persistência após refresh.
